    11→## Executive Summary
    12→
    13→This plan outlines a practical approach to building **security-focused LLM specialists** that can reliably beat frontier models on narrow, operational tasks. The key insight: you don't beat frontier models by training once—you build a **continuous specialization flywheel**.
    14→
    15→**Core Architecture:** CI/CD for Model Advantage
    16→1. Use frontier models as **teachers** (selectively)
    17→2. Generate **verifiable, domain-specific data** that general models don't have
    18→3. Train/refresh specialist models **regularly**
    19→4. Route requests to specialist OR frontier with **eval-driven gating**
    20→
    21→**Key Innovation:** The moat isn't "smarter weights"—it's **better verifiers + domain-specific data + faster iteration**.
    22→
    23→**Products:**
    24→1. **Detection Engineer Model** - Sigma/YARA rules, alert triage, IR playbooks
    25→2. **Secure Code Review Model** - Vulnerability patches, security review, CI copilot
    26→3. **CTF Operator Model** - Authorized red team assistance (sandboxed)
    27→
    28→**Expected Outcome:** Specialists that outperform frontier models on specific security tasks through verifiable, continuous improvement—not one-time training.
    29→
    30→**Training Platform:** [Atropos](https://github.com/NousResearch/atropos) - the LLM RL Gym framework in this repository. HYDRA environments are Atropos `BaseEnv` subclasses that generate rollouts for GRPO/DPO training.
    31→
    32→**Inspiration:** [Digital Red Queen](https://sakana.ai/drq/) - adversarial co-evolution produces more robust strategies than static benchmark optimization, even with smaller models.

    56→## 1. Continuous Specialization Flywheel
    57→
    58→### 1.1 The "Always Stay Ahead" Principle
    59→
    60→**Key Insight:** You don't beat frontier models by training once. You beat them by building a continuous specialization flywheel that:
    61→
    62→1. Uses the newest frontier models as **teachers** (selectively)
    63→2. Generates **verifiable, domain-specific data** that general models don't have
    64→3. Trains/refreshes specialist models **regularly**
    65→4. Routes requests to specialist OR frontier, with **eval-driven gating**
    66→
    67→**Think: "CI/CD for model advantage."**

   139→### 1.3 Teacher Refresh Protocol
   140→
   141→**When a new frontier model drops (e.g., Claude 5, GPT-6):**
   142→
   143→```python
   144→class TeacherRefresh:
   145→    """Protocol for refreshing specialists when new frontier drops."""
   146→
   147→    async def refresh_cycle(self, new_frontier_model: str):
   148→        # Step 1: Sample hard cases where specialist loses
   149→        hard_cases = await self.mine_failures(
   150→            specialist=self.current_specialist,
   151→            frontier=new_frontier_model,
   152→            n_samples=1000
   153→        )
   154→
   155→        # Step 2: Ask new frontier for better solutions
   156→        improved_solutions = await self.generate_with_teacher(
   157→            model=new_frontier_model,
   158→            hard_cases=hard_cases
   159→        )
   160→
   161→        # Step 3: Verify solutions (THE MOAT - no judge needed)
   162→        verified = []
   163→        for case, solution in zip(hard_cases, improved_solutions):
   164→            result = await self.verifier.verify(case, solution)
   165→            if result.passed:
   166→                verified.append((case, solution))
   167→
   168→        # Step 4: Add to dataset
   169→        self.dataset.add_preference_pairs(verified)
   170→
   171→        # Step 5: Run short preference optimization
   172→        new_specialist = await self.train_refresh(
   173→            base=self.current_specialist,
   174→            new_data=verified,
   175→            method="dpo",  # Quick refresh, not full retrain
   176→            epochs=1
   177→        )
   178→
   179→        # Step 6: Evaluate and ship
   180→        eval_results = await self.evaluate(new_specialist)
   181→        if eval_results.better_than(self.current_specialist):
   182→            self.deploy(new_specialist, version=self.next_version())
   183→```
   184→
   185→### 1.4 Why Specialists Beat Frontier
   186→
   187→| Factor | Generic Frontier Model | Your Specialist |
   188→|--------|----------------------|-----------------|
   189→| **Optimization target** | Broad helpfulness + safety | Your exact task metrics |
   190→| **Tool chain training** | Generic tool use | Your specific tools + workflows |
   191→| **Failure modes** | Doesn't know your edge cases | Trained on your failures |
   192→| **Feedback loop** | Updated every few months | Updated weekly |
   193→| **Verification** | Relies on RLHF | Deterministic verifiers |
   194→| **Telemetry formats** | Generic | Your exact log formats |
   195→| **False positive tuning** | Not a priority | Optimized for low FP |
   196→
   197→**The moat isn't "smarter weights." It's:**
   198→- Better data (domain-specific, continuously generated)
   199→- Better verifiers (deterministic, no judge bias)
   200→- Tighter task framing (exactly your workflow)
   201→- Faster iteration (weekly refresh vs monthly releases)

   278→from atroposlib.envs.base import BaseEnv, BaseEnvConfig, ScoredDataGroup
   279→
   280→class SecureCodeReviewEnv(BaseEnv):
   281→    """HYDRA Secure Code Review as Atropos environment."""
   282→
   283→    name = "secure_code_review"
   284→
   285→    async def get_next_item(self) -> Item:
   286→        """Sample next task from pool."""
   287→        return {"task_id": "sqli-001", "vulnerable_code": "..."}
   288→
   289→    async def collect_trajectories(self, item: Item) -> Tuple[ScoredDataGroup, List[Item]]:
   290→        """Generate patches, verify with harness, score."""
   291→        # 1. Generate patch candidates with training policy
   292→        patches = await self.generate_patches(item)
   293→
   294→        # 2. Verify each patch (exploit, tests, scanner)
   295→        results = [self.runner.run_task(item["task_id"], p) for p in patches]
   296→
   297→        # 3. Score and return ScoredDataGroup for GRPO
   298→        return self.build_scored_data_group(patches, results)
   299→```

   303→## 3. Product Verticals
   304→
   305→### 3.1 Product Strategy
   306→
   307→**Focus on narrow, operational security tasks where:**
   308→1. Success is **machine-verifiable** (tests, scanners, log replay)
   309→2. Generic models **don't have your data** (internal formats, edge cases)
   310→3. Tasks are **tool-grounded** (code execution, API calls)
   311→4. There's **clear ROI** (time saved, incidents prevented)
   312→
   313→### 3.2 Product 1: Detection Engineer Model (Blue Team)
   314→
   315→**Target users:** SOC analysts, detection engineers, threat hunters
   316→
   317→**Core tasks:**
   318→
   319→| Task | Input | Output | Verifier |
   320→|------|-------|--------|----------|
   321→| Log → Detection Rule | Zeek/Suricata/Sysmon logs | Sigma/YARA/Suricata rules | Replay logs, check triggers |
   322→| Alert Triage | Alert bundle + context | Prioritized hypotheses + steps | Simulated incident with ground truth |
   323→| Rule Optimization | Existing rule + FP examples | Refined rule | FP rate on test corpus |
   324→| IOC Extraction | Threat report | Structured IOCs | Format validation + known-bad matching |
   325→
   326→**Dataset generation pipeline:**
   327→
   328→```python
   329→class DetectionEngineerDataset:
   330→    """Generate verifiable detection engineering data."""
   331→
   332→    async def generate_log_to_rule_pairs(self):
   333→        # 1. Collect logs from diverse sources
   334→        logs = await self.collect_logs(sources=[
   335→            "zeek_samples", "sysmon_samples", "windows_security"
   336→        ])
   337→
   338→        # 2. For each attack type, generate rule candidates
   339→        for log_bundle in logs:
   340→            attack_type = self.classify_attack(log_bundle)
   341→
   342→            # Ask frontier to generate Sigma rule
   343→            rule_candidate = await self.frontier.generate(
   344→                f"Write a Sigma rule to detect this attack:\n{log_bundle}"
   345→            )
   346→
   347→            # VERIFY: Replay logs and check rule triggers
   348→            verification = await self.sigma_verifier.test_rule(
   349→                rule=rule_candidate,
   350→                positive_logs=log_bundle.attack_logs,
   351→                negative_logs=log_bundle.benign_logs
   352→            )
   353→
   354→            if verification.true_positive_rate > 0.95 and verification.false_positive_rate < 0.05:
   355→                self.dataset.add({
   356→                    "input": log_bundle,
   357→                    "output": rule_candidate,
   358→                    "verification": verification
   359→                })
   360→```
   361→
   362→**Why it beats frontier:**
   363→- Trained on **your exact telemetry formats** and tool chain
   364→- Optimized for **low false positives** (generic models aren't tuned for this)
   365→- Knows **your environment** (asset inventory, baseline behavior)
   366→- **Weekly refresh** on new attack patterns
   367→
   368→### 3.3 Product 2: Secure Code Review / Patch Engineer
   369→
   370→**Target users:** Security engineers, DevSecOps, AppSec teams
   371→
   372→**Core tasks:**
   373→
   374→| Task | Input | Output | Verifier |
   375→|------|-------|--------|----------|
   376→| Vulnerability Patch | Code + scan finding + exploit | Patched code + tests | Scanner clean + tests pass + exploit fails |
   377→| Security Review | PR diff | Security issues + fixes | Static analyzer + manual spot check |
   378→| Secure Refactor | Insecure pattern | Secure equivalent | Regression tests + security tests |
   379→| Dependency Fix | CVE + affected code | Updated deps + migration | Build passes + scanner clean |
   380→
   381→**Dataset generation pipeline:**
   382→
   383→```python
   384→class SecureCodeReviewDataset:
   385→    """Generate verifiable secure code review data."""
   386→
   387→    async def generate_patch_pairs(self):
   388→        # 1. Find vulnerable code samples
   389→        vuln_samples = await self.collect_vulnerable_code(sources=[
   390→            "cve_fixes",  # Historical CVE patches
   391→            "sast_findings",  # Static analysis findings
   392→            "ctf_challenges"  # CTF web challenges
   393→        ])
   394→
   395→        for sample in vuln_samples:
   396→            # 2. Ask frontier to generate patch
   397→            patch = await self.frontier.generate(f"""
   398→                Vulnerable code: {sample.vulnerable_code}
   399→                Vulnerability: {sample.vulnerability_description}
   400→                Generate: Patched code + test cases
   401→            """)
   402→
   403→            # 3. VERIFY: Multi-stage verification
   404→            verification = await self.verify_patch(
   405→                original=sample.vulnerable_code,
   406→                patched=patch.code,
   407→                tests=patch.tests
   408→            )
   409→
   410→            if verification.all_passed:
   411→                self.dataset.add({
   412→                    "input": sample,
   413→                    "output": patch,
   414→                    "verification": verification
   415→                })
   416→
   417→    async def verify_patch(self, original, patched, tests):
   418→        results = {}
   419→        results["exploit_original"] = await self.sandbox.run_exploit(original)
   420→        results["exploit_patched"] = await self.sandbox.run_exploit(patched)
   421→        results["regression"] = await self.sandbox.run_tests(patched, tests.regression)
   422→        results["scanner"] = await self.semgrep.scan(patched)
   423→
   424→        return VerificationResult(
   425→            all_passed=(
   426→                results["exploit_original"].succeeded and
   427→                not results["exploit_patched"].succeeded and
   428→                results["regression"].all_passed and
   429→                results["scanner"].findings == 0
   430→            )
   431→        )
   432→```
   433→
   434→**Why it beats frontier:**
   435→- **Deterministic evaluation** - you can grind improvement
   436→- Trained on **your stack** (frameworks, libraries, patterns)
   437→- Becomes a **CI security copilot** that's objectively better
   438→- Very strong ROI (vulnerabilities caught in CI vs production)

   475→## 4. Verifier Harnesses (The Moat)
   476→
   477→### 4.1 The Single Most Important Design Rule
   478→
   479→**Make your domain tasks machine-checkable.**
   480→
   481→If success depends on a **judge model**, your advantage gets eaten as soon as the next frontier model has better judging.
   482→
   483→If success depends on **tests, sandboxes, log replays, scanners**, you can keep compounding improvements cheaply.
   484→
   485→### 4.2 Verifier Stack
   486→
   487→```
   488→┌─────────────────────────────────────────────────────────────────────────┐
   489→│                        VERIFIER HARNESS STACK                            │
   490→├─────────────────────────────────────────────────────────────────────────┤
   491→│                                                                         │
   492→│  LAYER 1: Code Execution Sandbox                                        │
   493→│  ├── Docker containers with strict isolation                            │
   494→│  ├── Firecracker microVMs for untrusted code                           │
   495→│  ├── Resource limits (CPU, memory, time, network)                       │

   535→## 5. DRQ Adversarial Training
   536→
   537→### 5.1 Digital Red Queen Insight
   538→
   539→From [Sakana AI's DRQ paper](https://sakana.ai/drq/):
   540→
   541→> "Adversarial self-play produces more robust strategies than optimization against static benchmarks, even with smaller models."
   542→
   543→**Why this matters for HYDRA:**
   544→
   545→| Static Benchmark Training | DRQ Adversarial Training |
   546→|--------------------------|-------------------------|
   547→| Model learns to pass fixed test set | Model learns to beat evolving adversary |
   548→| Overfits to benchmark | Generalizes to novel attacks |
   549→| Plateaus when benchmark is "solved" | Arms race drives continuous improvement |
   550→| Hidden set is only defense against gaming | Gaming becomes the training signal |
   551→
   552→### 5.2 DRQ for Security Tasks
   553→
   554→HYDRA naturally has **adversarial pairs**:
   555→
   556→| Defender | Attacker | Arena |
   557→|----------|----------|-------|
   558→| Patch generator | Exploit mutator | Secure Code Review |
   559→| Detection rule writer | Evasion generator | Detection Engineer |
   560→| Defender playbook | Attack chain planner | CTF Operator |
   561→
   562→**DRQ Form 1 (MVP):** Fixed attacker
   563→- Train defender only
   564→- Attacker is heuristic or frontier model
   565→- Simpler, proves the loop works
   566→
   567→**DRQ Form 2 (Advanced):** Full co-training
   568→- Train both defender and attacker
   569→- True arms race like Sakana's Core War
   570→- More complex but potentially stronger
   571→
   572→### 5.3 DRQ in Atropos collect_trajectories
   573→
   574→```python
   575→async def collect_trajectories(self, item: Item) -> Tuple[ScoredDataGroup, List[Item]]:
   576→    """DRQ-style scoring in Atropos environment."""
   577→
   578→    # 1. Generate patches (defender)
   579→    patches = await self.generate_patches(item)
   580→
   581→    # 2. Verify with harness (static benchmark component)
   582→    harness_results = [self.runner.run_task(item["task_id"], p) for p in patches]
   583→
   584→    # 3. Run attacker against patches that pass harness (DRQ component)
   585→    attacker_results = []
   586→    for patch, result in zip(patches, harness_results):
   587→        if result.passed:
   588→            bypass = await self.run_attacker(patch, item)
   589→            attacker_results.append(bypass)
   590→        else:
   591→            attacker_results.append(None)
   592→
   593→    # 4. Score combines harness + attacker survival
   594→    scores = [
   595→        self.compute_drq_score(harness, attack)
   596→        for harness, attack in zip(harness_results, attacker_results)
   597→    ]
   598→
   599→    return self.build_scored_data_group(patches, scores)
   600→```
   601→
   602→### 5.4 Adversary Pool (Historical Opponents)
   603→
   604→DRQ's key mechanism: **new generations must beat historical opponents**.
   605→
   606→```python
   607→class AdversaryPool:
   608→    """Store successful attacks for future training."""
   609→
   610→    def __init__(self, max_size: int = 100):
   611→        self.pool: Dict[str, List[Dict]] = {}  # task_id -> attacks
   612→
   613→    def add_successful_attack(self, task_id: str, attack: Dict):
   614→        """When attacker bypasses a patch, store it."""
   615→        if task_id not in self.pool:
   616→            self.pool[task_id] = []
   617→        self.pool[task_id].append(attack)
   618→        # Trim to max size
   619→        self.pool[task_id] = self.pool[task_id][-self.max_size:]
   620→
   621→    def get_historical_attacks(self, task_id: str) -> List[Dict]:
   622→        """Get attacks that future patches must survive."""
   623→        return self.pool.get(task_id, [])
   624→```
   625→
   626→This prevents overfitting: patches must work against all historical attacks, not just current ones.

   654→## 7. Judge Reliability & Bias Mitigation
   655→
   656→### 7.1 Known LLM-as-Judge Biases
   657→
   658→| Bias Type | Description | Mitigation |
   659→|-----------|-------------|------------|
   660→| **Position Bias** | Prefers A or B based on order | Always evaluate both orders |
   661→| **Verbosity Bias** | Prefers longer answers | Length normalization |
   662→| **Self-Enhancement** | Prefers its own style | Use different judge than generator |
   663→
   664→### 7.2 Required Mitigations
   665→
   666→```python
   667→async def mitigated_judge(self, response_a, response_b, challenge):
   668→    """Always evaluate in both orders."""
   669→
   670→    verdict_ab = await self.judge.evaluate(first=response_a, second=response_b)
   671→    verdict_ba = await self.judge.evaluate(first=response_b, second=response_a)
   672→
   673→    if verdict_ab.winner == "first" and verdict_ba.winner == "second":
   674→        return {"winner": "A", "confident": True}
   675→    elif verdict_ab.winner == "second" and verdict_ba.winner == "first":
   676→        return {"winner": "B", "confident": True}
   677→    else:
   678→        return {"winner": None, "needs_escalation": True}
   679→```
   680→
   681→### 7.3 Judge Calibration (Week 0 Requirement)
   682→
   683→Before training, verify:
   684→- Position bias flip rate < 10%
   685→- Verbosity correlation < 0.3
   686→- Self-agreement > 95%

   691→
   692→### 8.1 Key Principle
   693→
   694→**Treat "evolution" as DATA evolution, not weight evolution.**
